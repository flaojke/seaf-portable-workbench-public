# Проверка удобства и соответствия вариантов

Проверены [organization.md](organization.md), [fixtures.mjs](fixtures.mjs) и [analyze.mjs](analyze.mjs). Это статическое сопоставление структуры, владения и текста рекомендаций. Новые runtime-измерения и пользовательские сессии не выполнялись; качественные оценки не являются результатами исследования с пользователями.

## Четыре пользовательских варианта и рекомендуемый гибрид

| Вариант | Каноническое размещение и ownership | Удобство сопровождения | Ограничения |
|---|---|---|---|
| **1 / v1:** плоские файлы систем через общий `systems.yaml` | Система — собственный leaf-файл; интеграции — общий `integrations.yaml`. Владение системами назначается по файлам, а интеграции требуют отдельного процесса review | Систему легко найти и изменять независимо; индекс состава отделён от корня | Новые системы меняют общий индекс. Общие интеграции остаются точкой пересечения владельцев; документацию и дополнительные артефакты сложнее держать рядом с системой |
| **2 / v2:** те же файлы, прямые импорты из `root.yaml` | Те же определения и ownership, что в v1; меняется только место перечисления leaf-файлов | Включение каждого файла видно непосредственно из корня | Корень содержит длинный технический список и меняется при добавлении систем. Прямой импорт сам по себе не решает совместное владение интеграциями |
| **3 / v3:** папка системы с типизированными файлами, прямые импорты из корня | Система и её исходящие интеграции расположены рядом; удобно назначить владельца папки | Хорошая локальность исходников и сопутствующих документов; граница ответственности видна в дереве | Корень знает внутренние файлы каждой системы. Добавление нового типа файла требует обновления общего списка; нужны правила единственного владельца интеграции |
| **4 / v4:** те же папки через общие агрегаторы типов | Папки сохраняют локальных владельцев; состав файлов систем и интеграций находится в двух общих индексах | Корень остаётся небольшим; виден полный состав каждого типа артефактов | Одна логическая система отражается в нескольких индексах. Изменения состава модуля затрагивают общие файлы, хотя payload принадлежит конкретной команде |
| **Гибрид:** небольшие пакеты домена + отдельные папки и manifests сложных систем | Владение определяется реальными доменами/командами; исходящие интеграции принадлежат источнику. Сложная система включается одним manifest | Баланс обзорности, локальности документов и объёма технических индексов; структуру можно подстроить под команды | Пакет увеличивает область совместного редактирования. Manifest системы добавляет артефакт и import edge; размер пакета не следует считать универсальным оптимумом |

Дополнительный `v5` — собственный manifest каждой системы; `v6` — пакеты фиксированного размера. Они не подменяют нумерацию четырёх пользовательских вариантов. В проверенной редакции `organization.md` и в `analyze.mjs` пользовательские варианты v1–v4 перечислены отдельно.

Удобство гибрида — рекомендация по сопровождению, а не вывод о безусловной победе по скорости. Фактический v6 группирует последовательные ID по 20; владельцы в модели распределены между командами. Он проверяет физическую упаковку файлов, а не качество выделения настоящих бизнес-доменов.

## Импорты и канонический владелец

Относительные пути в примерах согласованы с папками содержащих их manifests:

| Файл-источник | Импорт | Разрешённый путь от корня примера |
|---|---|---|
| `root.yaml` | `domains/commerce/root.yaml` | `domains/commerce/root.yaml` |
| `domains/commerce/root.yaml` | `systems/checkout/root.yaml` | `domains/commerce/systems/checkout/root.yaml` |
| `domains/commerce/systems/checkout/root.yaml` | `systems.yaml` | `domains/commerce/systems/checkout/systems.yaml` |
| `domains/commerce/systems/checkout/view.yaml` | `../../../../common/catalogs.yaml` | `common/catalogs.yaml` |
| Тот же `view.yaml` | `../../../logistics/root.yaml` | `domains/logistics/root.yaml` |

Аналогично примеры `analyze.mjs` разрешают `shared/root.yaml` от корня, `lti/root.yaml` от `domains/logistics` и typed-файлы от папки LTI. Пути явные, без glob. Общие catalogs/schema/rules подключаются один раз на выбранный граф сборки. Вспомогательный read-only entrypoint не включается одновременно с основным модулем в основной граф.

Правило «владелец интеграции — источник» применено последовательно: запись находится в модуле источника или его доменном пакете, а получатель участвует в review контракта и ссылается на тот же ID. CODEOWNERS помогает направить review, но не заменяет обязательные approvals, Git-права или ACL портала.

Если интеграции живут в `components.*.links`, этот массив должен иметь один сопровождаемый источник. Если используется отдельная сущность интеграции, её схема и имя сохраняются. В fixtures integration-объект и соответствующий link создаются из одного генератора: это два представления одного взаимодействия, а не удвоенное количество бизнес-интеграций.

## Границы применимости и оговорки

- В измерительной модели есть `components`, custom `integrations`, `contexts`, `docs`, `catalogs` и определение integration-схемы. **Функции и самостоятельные информационные потоки не моделировались**. Файлы `functions.yaml` и `flows.yaml` в рекомендуемом дереве — организационный пример для проекта, где такие сущности действительно существуют; измерения не доказывают стоимость их загрузки.
- Показаны DocHub-совместимые `components` и синтетическая custom integration-схема. Корпоративные имена сущностей, поля, справочники и правила нужно сохранить, а не переименовать по примеру файлов.
- ID-ссылки сохраняются при чистом перемещении определения, но raw-file URL и относительные ссылки документов проверяются отдельно. Манифест-переходник подходит только клиенту, понимающему SEAF imports.
- Папка отдельной системы может требовать общих каталогов и зависимых систем. Для автономного read-only представления нужны замкнутый набор зависимостей и общий разрешённый workspace; одна папка не становится самодостаточным или защищённым подрепозиторием автоматически.
- Единицы масштаба уточнены: исходная модель содержит 100 **систем** / 300 **интеграций**; размеры партий миграции выбираются отдельно. Редакция `organization.md` исправлена, чтобы не трактовать эти числа как два этапа по 100 и 300 систем. Будущее масштабирование описано отдельно.

Для итогового решения рекомендуется опираться на реальные границы владения, удобство чтения отдельного объекта, ограничения редактора и измеренные режимы загрузки. Результаты local-file, контролируемого HTTP и raw-source API нельзя превращать в утверждение о производительности конкретного GitLab, clone/fetch или любой корпоративной метамодели.
