# Организация архитектурного репозитория SEAF

Этот документ сравнивает удобство сопровождения файлов. Он не ранжирует варианты по скорости: время загрузки, проверки, обновления и отображения нужно брать из отдельного протокола измерений на эквивалентных моделях.

Имена `systems.yaml`, `integrations.yaml` и каталогов — организация исходников, а не названия сущностей метамодели. В примерах систем используется реальный раздел DocHub `components`; в другом проекте он может соответствовать сущности SEAF с иным именем. Перед переносом нужно сохранить фактические разделы, поля и ID проекта. Не следует переименовывать их в `systems` только ради имени файла.

## Четыре пользовательских варианта

В стенде им соответствуют несколько вариантов; одинаковая логическая модель позволяет отдельно оценить влияние структуры импортов.

| Подход | Вариант стенда | Удобство | Что усложняется |
|---|---|---|---|
| Плоские файлы систем, общий `systems.yaml` импортирует их | `v1` | Файл конкретной системы легко найти; состав систем собран в одном индексе; команды могут редактировать разные файлы | При добавлении системы меняется индекс. Интеграции остаются в общем файле, поэтому владение ими менее локализовано |
| Те же плоские файлы импортирует непосредственно корень | `v2` | Простой граф импортов; для каждого файла видно прямое включение в сборку | Корневой manifest превращается в длинный технический список. Несколько команд меняют один файл состава репозитория |
| Папка системы с типизированными файлами; корень импортирует leaf-файлы напрямую | `v3` | Определения системы, её исходящие интеграции и сопутствующие артефакты находятся рядом; удобно назначать владельца папки | Корень знает внутренний состав каждой папки. Новый типизированный файл требует изменения корневого списка |
| Те же папки, включённые через общие `systems.yaml` и `integrations.yaml` | `v4` | Локальность папки сохраняется, а корень подключает небольшое число общих индексов | Состав одной системы распределён между несколькими индексами. Добавление файлов модуля затрагивает общие списки |

`baseline` с двумя крупными типизированными файлами удобен как исходная точка сравнения и для небольших моделей. Его ограничения при совместной работе — общий файл для многих владельцев и необходимость искать объект внутри большого документа.

Дополнительный `v5` использует собственный `root.yaml` каждой системы. У модуля появляется явная точка входа, а его внутренние изменения не требуют перечислять все leaf-файлы в общем корне. Цена организации — дополнительные manifests; сама папка всё ещё может зависеть от общих каталогов и систем-получателей.

Дополнительный `v6` группирует системы и исходящие интеграции в **пакеты фиксированного размера 20** с локальными manifests. Группы формируются из последовательных ID, а владельцы в синтетической модели распределены между командами. Поэтому v6 проверяет физическую упаковку файлов, а не выделение настоящих бизнес-доменов или границ владения. Размер пакета — экспериментальный параметр, а не универсальная норма.

## Рекомендуемый баланс: домены и отдельные модули сложных систем

Базовая единица владения — домен или команда. Простые системы одного владельца можно хранить вместе в типизированном файле домена. Систему с большим объёмом собственной документации, несколькими схемами или отдельным циклом изменений стоит выделить в папку с manifest.

Такой гибрид удобнее выбирать по границам ответственности. Увеличение количества файлов само по себе не делает модель более модульной, а объединение файлов не меняет семантику архитектурных связей.

```text
project/
  root.yaml
  common/
    catalogs.yaml
  metamodel/
    integrations.yaml
  views/
    root.yaml
  domains/
    commerce/
      root.yaml
      systems.yaml
      integrations.yaml
      systems/
        checkout/
          root.yaml
          systems.yaml
          integrations.yaml
          docs/
            overview.md
    logistics/
      root.yaml
      systems.yaml
      integrations.yaml
```

Это пример структуры сопровождения, а не ещё один вариант измерительного стенда. В примере `checkout` вынесен из общего файла систем домена: одну и ту же систему не нужно одновременно объявлять в обоих местах.

### Корневой manifest

`project/root.yaml`:

```yaml
imports:
  - common/catalogs.yaml
  - metamodel/integrations.yaml
  - domains/commerce/root.yaml
  - domains/logistics/root.yaml
  - views/root.yaml
```

Общие каталоги и определения метамодели подключаются здесь один раз. Дочерние manifests не должны повторно импортировать общий корень или одни и те же каталоги. Граф импортов должен быть направленным и не содержать повторных включений и циклов.

### Manifest домена

`project/domains/commerce/root.yaml`:

```yaml
imports:
  - systems.yaml
  - integrations.yaml
  - systems/checkout/root.yaml
```

`project/domains/logistics/root.yaml`:

```yaml
imports:
  - systems.yaml
  - integrations.yaml
```

В общем `commerce/systems.yaml` находятся только системы, которые не вынесены в самостоятельные модули. Соответственно, `commerce/integrations.yaml` не дублирует исходящие интеграции `checkout`, если они принадлежат его модулю.

### Manifest системы

`project/domains/commerce/systems/checkout/root.yaml`:

```yaml
imports:
  - systems.yaml
  - integrations.yaml
```

Пример `systems.yaml` для DocHub-профиля:

```yaml
components:
  checkout:
    title: Оформление заказа
    entity: system
    owner: Commerce
```

ID `checkout` здесь условный. При миграции существующего проекта нужно оставить его исходный ID, включая имеющиеся пространства имён и контейнерные компоненты.

Пример отдельного реестра интеграций:

```yaml
integrations:
  checkout_to_delivery:
    title: Передача оплаченного заказа
    from: checkout
    to: delivery
    protocol: HTTPS
```

Раздел `integrations` в этом фрагменте — иллюстрация отдельной сущности с подключённой схемой `metamodel/integrations.yaml`; именно такой отдельный раздел используется в синтетических fixtures. Он не объявляется встроенным стандартом всех SEAF-проектов. Если реальный проект использует, например, собственную интеграционную сущность SEAF, нужно сохранить её имя и её схему.

В DocHub-проекте взаимодействие может храниться только в `components.<id>.links`. Тогда канонический источник связи — файл компонента-источника. Не нужно создавать второй вручную сопровождаемый реестр с теми же фактами ради наличия `integrations.yaml`. Если нужны обе формы представления, одна должна вычисляться из другой, а правило преобразования и стабильный ID интеграции должны быть явными. Отдельные integration-объекты сами по себе не гарантируют появления линий в существующей диаграмме компонентов.

Все `imports` в примерах перечислены явно. Они разрешаются относительно файла, содержащего список. В данном процессе сборки нельзя полагаться на `*.yaml`, автоматическое сканирование папки или интерпретацию Windows-пути как URL. Для импортов используются относительные пути с `/`, для соединений между сущностями — стабильные ID.

## Один канонический владелец интеграции

Правило по умолчанию: интеграцией владеет система-источник, а физически она хранится в модуле источника или в пакете его домена.

Например, взаимодействие `checkout → delivery` хранится у `checkout` в Commerce. Logistics согласует контракт получателя, но не создаёт вторую копию той же интеграции в своей папке. Иначе при изменении протокола, владельца данных или назначения связи появятся две конкурирующие версии истины.

Для общей инфраструктурной интеграции владелец может быть назначен явно по другому правилу. Исключение записывается в принятом соглашении о моделировании; канонический объект и его ID всё равно остаются единственными.

В выборках и каталогах другого домена следует показывать ссылку на тот же объект или вычисляемое представление. Дублирование записи с другим ID ради отображения в двух местах затрудняет поиск расхождений, анализ зависимостей и последующие изменения через агента.

## Владение файлами и review

Владение бизнес-системой в модели и владение исходным файлом в Git — связанные, но разные понятия. Каталог `teams` не назначает Git-права автоматически. Папки и CODEOWNERS также не являются разграничением доступа к данным в портале.

Пример правил CODEOWNERS; имена групп условные:

```text
*                                             @org/architecture-platform
/root.yaml                                    @org/architecture-platform
/common/                                      @org/architecture-platform
/metamodel/                                   @org/architecture-platform
/domains/commerce/                            @org/commerce-architecture
/domains/logistics/                           @org/logistics-architecture
/domains/commerce/systems/checkout/            @org/checkout-team
```

Размещение CODEOWNERS, разрешение пересекающихся правил и обязательность approval нужно проверить на используемой Git-платформе. Само наличие этого файла не гарантирует нужную политику согласования: отдельно настраиваются защищённая ветка и обязательные проверки.

Практическое разделение review:

- Владелец системы проверяет её назначение, свойства, интерфейсы и исходящие связи.
- Команда получателя согласует изменения междоменных контрактов, данных и ограничений взаимодействия.
- Команда платформы архитектуры проверяет изменения метамодели, общих справочников и корневого состава сборки.
- Автоматические проверки подтверждают корректность импортов, схем, ссылок и модели. Они не заменяют содержательное согласование контракта.

Если нужно согласование сразу двух команд, его следует задать отдельным правилом review в Git-платформе, а не предполагать, что перечисление нескольких владельцев в одной строке обязательно потребует все approvals.

## Подключение отдельной системы как read-only проекта

`systems/checkout/root.yaml` показывает локальный состав модуля. Он может зависеть от общих каталогов, схем и систем-получателей, поэтому его самостоятельная загрузка не обязана совпадать с загрузкой полного проекта.

Для отдельного представления можно создать специальный entrypoint, который включает модуль и необходимые зависимости, и подключить его только для чтения. Общий Windows workspace должен охватывать все такие файлы; одного выбора папки системы недостаточно, если разрешённая область импортов ею ограничена.

Например, отдельный `project/domains/commerce/systems/checkout/view.yaml` может содержать:

```yaml
imports:
  - root.yaml
  - ../../../../common/catalogs.yaml
  - ../../../../metamodel/integrations.yaml
  - ../../../logistics/root.yaml
```

Последний путь из папки `domains/commerce/systems/checkout` указывает на `domains/logistics/root.yaml`. Этот модуль нужен только если его сущности действительно являются зависимостями выбранной системы; состав зависимостей нужно довести до замкнутого набора, а не включать произвольные соседние папки.

Для такого подключения корневой манифест проекта — `view.yaml`, общий validation workspace — `project`, а runtime manifest — `workspace/domains/commerce/systems/checkout/view.yaml`. Общий корень основного проекта не импортирует этот вспомогательный `view.yaml`: он по-прежнему включает `checkout/root.yaml`, поэтому каталоги не дублируются в основной сборке.

Альтернатива — оставить корень проекта общим и подключить отдельный entrypoint из `views`. Это удобнее, когда зависимости модуля велики. Read-only представление не является способом скрыть остальные файлы от пользователя, уже имеющего доступ к общему workspace.

Если планируются изменения через редактор или MCP, нужно отдельно выбрать правильный writable корень и права на зависимые объекты. Подключение папки системы не должно автоматически давать право менять общие каталоги или соседние системы. Источник фактов MCP по импортам и полный runtime с подключённой метамоделью также следует различать при проверке результата.

## Миграция текущей модели: 100 систем / 300 интеграций

Исходный объём этой задачи — 100 систем и 300 интеграций. Это не два этапа по 100 и 300 систем. Перенос файлов не должен менять общее количество объектов, их ID или смысл взаимодействий; размер одной партии выбирается отдельно по владельцу и числу затронутых файлов.

1. Зафиксировать исходное состояние: Git commit, используемую метамодель и runtime, полный граф импортов, список сущностей и связей. Выполнить обычную проверку модели и сохранить её результат.
2. Создать отдельную ветку `codex/reorganize-project-layout` и рабочую копию для реорганизации. Не перемещать файлы в опубликованной папке параллельно с её загрузкой порталом.
3. Выбрать небольшой пилот по владельцу или домену, например 5–10 существующих систем с их фактическими исходящими интеграциями. Перенести полные определения без смены ID, типов и значений свойств; одновременно удалить перенесённые записи из прежнего общего файла. Размер партии согласуется с ограничениями инструмента на количество изменяемых файлов.
4. Обновить явные `imports`. Системы вне пилотной партии остаются в исходных пакетах. Не оставлять пустые файлы-пустышки и не включать одновременно старый и новый путь к одному модулю.
5. Проверить логическую эквивалентность и валидаторы, затем изучить файловый diff и provenance. Количество изменённых строк может быть большим; семантический diff при чистом переносе должен быть пустым.
6. Открыть представления выбранных систем, связи и общие контексты. Проверить переходы по ID и необходимые raw-file ссылки. Убедиться, что сценарии и документы по-прежнему доступны.
7. Сохранить целостный перенос пилотной партии одним reviewable Git-коммитом и обновить портал один раз после завершения записи файлов. Git push и публикация ветки выполняются отдельно по принятому процессу.
8. Повторять перенос по владельцам, пока не будут организованы все исходные 100 систем и 300 интеграций. После каждой партии сравнивать полную модель с тем же исходным состоянием, а не только перенесённый фрагмент.

Для проверки эквивалентности полезны одновременно несколько уровней:

- Канонический hash объединённой модели исходных артефактов, без учёта расположения файлов и порядка ключей mapping.
- Отдельное сравнение систем, интеграций, направлений связей и значимых свойств; порядок массивов сохраняется.
- Контроль количества реальных систем и интеграций, без подмены дополнительными контейнерными объектами.
- Проверка проекта настоящим SEAF runtime с теми же общими зависимостями и метамоделью.
- Smoke-проверка интерфейса и API, которые используют эти данные.

При сравнении полного runtime нужно учитывать, что он добавляет встроенную метамодель. Нельзя сравнивать его целиком с project-local JSON и считать различие автоматически ошибкой миграции. Для двух runtime-состояний сравниваются одинаковые логические разделы при одинаковой конфигурации; ссылки на исходные файлы ожидаемо изменятся.

Особое внимание нужно массивам: некоторые операции объединения импортов дополняют массив, а не заменяют его. Двойное подключение `links` может удвоить взаимодействия при сохранении тех же ID компонентов. Поэтому каноническое определение связи должно находиться в одном месте.

### Отдельно: будущее масштабирование

При дальнейшем росте числа систем можно выделять новые пакеты и самостоятельные модули по реальной ответственности. Это отдельная эволюция структуры, а не продолжение миграции «до 300 систем». Синтетические нагрузочные стенды большего размера проверяют техническую масштабируемость; они не устанавливают оптимальную бизнес-границу домена и не требуют менять число объектов текущего проекта.

## Что сохраняется при перемещении файлов

Связи и API, основанные на стабильных ID сущностей, не требуют изменения из-за нового физического пути. Но raw-file URL, относительные ссылки Markdown, пути к схемам, изображениям, `$ref` и корневым manifests требуют отдельной проверки. Нельзя обещать неизменность файлового API только потому, что ID систем сохранены.

Если старый путь используется внешними SEAF-импортами, можно временно оставить manifest-переходник со ссылкой на новое каноническое расположение. Его не нужно одновременно включать с новым путём в одну сборку. Такой переходник сохраняет импортную точку входа SEAF, но не байтовый формат старого YAML для клиента, ожидающего inline-объекты.

Откат выполняется целостным возвратом миграционного коммита и перезагрузкой прежнего manifest. Не следует вручную копировать часть старых файлов поверх новой схемы импортов: это может вернуть дубли определений и связей.
