В src/global/jsonata/driver.mjs:49 функция wcard разбивает шаблон и создаёт новый RegExp при каждом вызове. В public/metamodel/dochub/rules/validators.yaml:29 правило archtool.metamodel.contexts.outof выполняет для каждого компонента фильтр по всем distinct(contexts.*.components). В этих fixtures full содержит N точных ID, focus — 50 из них; получается N уникальных масок, и статическая структура выражения предполагает N × N проверок: 1 млн при N=1000 и 9 млн при N=3000. Это вывод из кода и данных, не измеренный счётчик вызовов. В backend/storage/manager.mjs applyManifest ожидает validators и вне условия warmupNeeded.

Горячая lookup в node_modules/jsonata/jsonata.js:5338 ищет переменную в environment bindings, поэтому её нельзя автоматически считать модельной функцией $lookup. GC занимает 9.55%; профиль не даёт права приписывать весь GC только RegExp.

Чтение четырёх fixture YAML заняло суммарно 13.6 мс; YAML.parse — 783.6 мс под profiler. Вместе с горячими функциями это указывает на стоимость вычислений/валидации, а не на чтение четырёх файлов как основной bottleneck. Эти инструментированные parse timings нельзя смешивать с неинструментированными медианами основной серии.

Рост полного reload примерно в семь раз при росте N втрое согласуется с таким квадратичным участком плюс фиксированной/линейной работой. Единственный профиль не доказывает точную асимптотику всей системы и не изолирует стоимость каждого правила.

Кандидат отдельной последующей оптимизации: индекс точных ID, отдельная обработка wildcard-масок, ограниченный кеш компиляции шаблонов и прекращение поиска после первого совпадения. Нужна проверка эквивалентности находок для точных ID, * и **, вложенных идентификаторов и отсутствующих компонентов. В исследовании это не внедрялось; frozen product/worker не менялись.
