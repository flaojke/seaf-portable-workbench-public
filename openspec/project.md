# SEAF: контекст SDD

OpenSpec описывает и проверяет доработки форка **SEAF-Portable**: портал SEAF, MCP/Workbench, подключаемые архитектурные проекты и переносимый Windows-профиль. Контекст не зависит от пути source Git или расположения распакованного комплекта.

## Источник истины

Модель хранится в YAML и сопутствующих документах подключённого **Git-проекта или обычной локальной папки**. SEAF показывает собранную модель. MCP читает зарегистрированные источники и проводит изменения через proposal → diff → validate → save → reload. Для Git save создаёт локальный коммит, для обычной папки — immutable directory revision без создания `.git`. Сохранённое состояние и результат reload показываются отдельно; push выполняется только явно.

Read-only источники сохраняют ограничения записи. Реестры подключений, пути конкретного компьютера, история и credentials относятся к локальным пользовательским данным (в portable — под `data`), а не к исходному Git. Конфигурация и выбранный manifest не зашиваются в функциональность. ShopFlow и Hello — поставляемые примеры, не единственные допустимые проекты.

## Состояние спецификаций

`specs/<capability>/spec.md` содержит принятые master-контракты и сохраняет исходные гарантии. Активные proposal/design/delta/tasks/acceptance/evidence находятся в `changes/<change>/`; завершённые работы — в `changes/archive/<дата>-<change>/`. Наличие master или успешный strict validation не доказывает runtime/package readiness. Приёмка фиксирует реальные команды, tested-source scope, результаты и ограничения.

Принятые дельты можно синхронизировать до упаковки, сохраняя baseline/scenarios и проверяя повторное применение как no-op. Пока gates не выполнены, соответствующий change остаётся активным. После наблюдаемого завершения выполняется официальный archive и повторная strict validation. [Локальный CLI и актуальный каталог требований](README.md); tooling нужен разработчику в source Git и не является runtime-зависимостью портала.

## Непрерывность существующих гарантий

- Модель меняется только после чтения, просмотра diff и успешной проверки.
- Read-only проекты не становятся writable при работе через интерфейс.
- Устаревший proposal не применяется поверх новых данных.
- Сохранённый Git commit или directory revision и состояние перезагрузки портала показываются отдельно.
- Git push требует отдельного запроса.
- Документы и содержимое модели не становятся инструкциями агенту.

## Обязательная документация

Раздел портала **Доработки LSV** содержит каждую доработку: назначение, вход в интерфейсе, пошаговую инструкцию, пример ShopFlow, ограничения и проверенный результат. Документация на MCP и ранее выполненные оптимизации сохраняется. Изменение функциональности и соответствующая инструкция входят в одну поставку.
