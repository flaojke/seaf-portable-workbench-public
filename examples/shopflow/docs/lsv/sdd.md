# SDD и OpenSpec: порядок доработок

Feature: **SDD**. Capability: `sdd`.

Откройте [рабочее пространство SEAF](/entities/docs/blank?dh-doc-id=local.lsv.workbench) или [отдельную вкладку](http://localhost:8091). Выберите нужный проект; ниже пример для ShopFlow.

Доработки рабочего пространства описываются через OpenSpec: требования, дельты, технические решения, задачи и приёмку. Это помогает отличать реализованные гарантии от планируемых функций.

## Где лежат документы

Корень: `./openspec`.

- `config.yaml` — schema spec-driven, контекст и правила.
- `specs/<capability>/spec.md` — мастер-спецификации текущих контрактов поставки, сохраняющие исходные гарантии.
- `changes/<change>/proposal.md` — зачем и что меняется в активной работе; материалы закрытых изменений находятся в `changes/archive/<date>-<change>/`.
- `design.md` — технические решения и ограничения.
- `specs/<capability>/spec.md` внутри change — ADDED Requirements.
- `tasks.md` — работы с отметками только после проверки.
- `acceptance.md` — проверяемые сценарии и реальные доказательства.
- `validation.json` — результат структурной проверки OpenSpec.

## Как вести изменение

1. Прочитайте мастер-спецификацию и текущую дельту.
2. Опишите поведение через **Requirement** с SHALL/MUST и **Scenario** с WHEN/THEN.
3. Подготовьте/обновите proposal, design и tasks.
4. Реализуйте поведение, выполните сценарии и сохраните реальные результаты.
5. Обновите инструкцию в **Доработки LSV**: как использовать, пример ShopFlow, ограничения.
6. После приёмки синхронизируйте дельту в master штатным sync workflow и архивируйте завершённый change. Не помечайте функцию готовой только потому, что написана спецификация.

## Пример ShopFlow

Для добавления команды-владельца в редакторе найдите delta `object-editing/spec.md`: сценарий **Edit a system owner**. Подготовьте правку `demo.shop.delivery`, покажите semantic/file diff, проверьте runtime SEAF, сохраните commit и статус reload.

В acceptance запишите project, команду/шаги, наблюдаемый результат, commit и ссылку на log/screenshot. Для отказа stale proposal нужен отдельный отрицательный прогон на временном проекте. Страница **Точечные и пакетные изменения** документирует пользовательский путь.

## Проверка на Windows

Официальный CLI установлен локально, версия зафиксирована на 1.16.0; требуется Node 22.12+. Из `.`:

```powershell
$env:OPENSPEC_TELEMETRY = '0'
$env:OPENSPEC_NO_UPDATE_CHECK = '1'
node ./openspec/tooling/node_modules/@fission-ai/openspec/bin/openspec.js list --specs
node ./openspec/tooling/node_modules/@fission-ai/openspec/bin/openspec.js list
node ./openspec/tooling/node_modules/@fission-ai/openspec/bin/openspec.js validate --all --strict --no-interactive
```

Проверка охватывает 11 masters и активный change; после архивирования отдельно проверяются masters и сам каталог архивного изменения. Это проверка структуры документов. Продуктовая приёмка подтверждается отдельными запусками, журналами, Git-коммитами и статусом портала.

## Завершение поставки

2026-11-04 выполнен sync: 36 принятых требований изменения `add-architecture-workbench` включены в 11 master-спецификаций. Исходные baseline-гарантии сохранены; masters теперь описывают текущую поставку. ADDED-дельты сохранены в архиве как уже синхронизированная история — повторно добавлять их в masters не нужно.

05.11.2026 приёмка расширена браузерными и аварийными проверками: перенос и отказ хранилища черновиков, readonly, диагностика и retry, полный Git/reload цикл, восстановление после ошибки reload, снимки и preview, источники AI и редактирование draw.io. Матрица `coverage-all72.json` связывает каждый функциональный сценарий с конкретным доказательством. В ней различаются unit/API, браузер, реальный Docker/Git и ручная проверка внешнего MCP-агента: это не утверждение, что все 72 сценария вручную прошли через один интерфейс.

Закрытие включает финальный нативный прогон, публикацию этих инструкций через MCP и официальный CLI archive. Материалы закрытого change находятся под `openspec/changes/archive/`, включая локальные копии JSON/TAP-доказательств. Для этой поставки дельты уже синхронизированы; архивирование выполняется с `--skip-specs`, чтобы повторно не добавлять ADDED-блоки в masters. Фактический результат CLI и публикации фиксируется в evidence; наличие подготовленного файла само по себе не означает, что archive выполнен.

OpenSpec не заменяет Git, runtime validation и MCP-порядок изменения модели. Документы спецификаций, снимки и черновики сами по себе не выполняют commit или push.
