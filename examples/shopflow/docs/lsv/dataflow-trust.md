# Потоки данных и зоны доверия

Feature: **20**. Capability: `dataflow-trust`.

Откройте [рабочее пространство SEAF](/entities/docs/blank?dh-doc-id=local.lsv.workbench) или [отдельную вкладку](http://localhost:8091). Выберите нужный проект; ниже пример для ShopFlow.

Раздел использует те же components.links и добавляет компонентам trustZone и dataClassification. Межзонные связи выделяются на графе и в таблице. Явные trustPolicies проверяют отдельные аннотированные потоки.

## Как пользоваться

1. Откройте **Данные и доверие**.
2. Постройте подграф по компоненту, глубине и направлению.
3. В блоке **Свойства зоны и данных** укажите ID, зону и классификацию.
4. Нажмите **Подготовить изменение**, изучите diff.
5. Проверьте и примените черновик обычным путём.
6. После обновления перестройте граф и посмотрите межзонные связи.

Доступные классы: **Публичные**, **Внутренние**, **Конфиденциальные**, **Ограниченный доступ**. Название зоны — строка вашей модели, например internal или partner.

## Пример ShopFlow

Для учебного анализа назначьте `demo.shop.orders` зону `internal`, классификацию `confidential`, а `demo.shop.delivery` — зону `logistics`, классификацию `confidential`. Это именно изменения модели, поэтому перед применением проверьте их соответствие вашему примеру.

Постройте граф с фокусом `demo.shop.delivery`, глубиной **1** и всеми связями. Связь Delivery → Orders будет выделена как пересечение границы, потому что trustZone отличаются. Если одна зона не заполнена, пересечение не выводится — это отсутствие данных, а не подтверждение безопасности.

## Данные отдельных интеграций

На links можно хранить protocol, dataClassification и encrypted через универсальный редактор JSON. При изменении links передайте полный список, поскольку merge заменяет массив целиком. В **Данные компонентов и связей** видны аннотации каждого потока, статус политики и источники. Отдельной формы изменения каждого link пока нет.

## Пример политики

В **Объекты** создайте раздел **trustPolicies**, ID `logistics-to-internal`, объект:

```json
{
  "classification": "confidential",
  "fromZone": "logistics",
  "toZone": "internal",
  "requireEncryption": true,
  "allowedProtocols": ["HTTPS"]
}
```

Для потока Delivery → Orders задайте в его элементе links `dataClassification: "confidential"`, `protocol: "HTTPS"`, `encrypted: true`. Сохраняйте остальные links. Подготовьте diff, проверьте и примените изменения. После построения графа соответствующий поток может получить allowed; если encrypted не true либо протокол не из разрешённых, появится violation. `deny: true` в подходящей политике запрещает пересечение.

Подготовленный proposal с такой violation не пройдёт **Проверить в SEAF**: до запуска контейнера проверка целостности анализирует trustPolicies и отсутствующие endpoints. В выводе будет `workbench.model-integrity`; сохранить невалидное предложение в Git нельзя. Исправьте аннотации/связи или пересмотрите саму политику и подготовьте новый diff.

Политика сопоставляется по явным classification/fromZone/toZone. Пустые аннотации дают unknown. Классификация самого компонента не подставляется автоматически как классификация каждого потока.

## Ограничения

Пересечение границы не означает уязвимость. Проверки выполняются по объявленным полям и включённым политикам, не по реальному сетевому трафику. Система различает unknown, internal, review, allowed и violation. Отсутствие подходящей политики не является разрешением по умолчанию.

Явные нарушения подходящих trustPolicies блокируют публикацию в общем validation lifecycle; runtime-валидаторы SEAF затем выполняют остальные проверки. Отсутствующая классификация остаётся unknown и не превращается автоматически в violation любой возможной политики. Система не меняет настройки микросервисов и не подтверждает фактическое шифрование трафика.
