# Поиск противоречий между источниками

Feature: **AI-8**. Capability: `source-contradictions`.

Откройте [рабочее пространство SEAF](/entities/docs/blank?dh-doc-id=local.lsv.workbench) или [отдельную вкладку](http://localhost:8091). Выберите нужный проект; ниже пример для ShopFlow.

Проверка ищет несколько определённых типов несогласованности и показывает источники находок. Она не редактирует модель автоматически и не претендует на понимание всех документов.

## Как пользоваться

1. Выберите проект и откройте **Ассистент**.
2. Нажмите **Найти противоречия**.
3. Изучите тип, видимый статус confirmed/candidate, пояснение uncertainty и фрагменты sources.
4. Подтвердите, что оба источника описывают один объект и одну версию требований.
5. Для исправления используйте **Объекты** или внешнего MCP-агента; подготовьте отдельный diff и пройдите runtime validation.

## Что проверяется сейчас

**owner-disagreement**: исходные YAML-импорты задают разные явные owner одного section/ID. Такой конфликт значений помечается confirmed с обеими сторонами источников до слияния. Переопределение может быть намеренным — оцените его смысл и порядок импортов.

**Документный owner-disagreement**: явная строка owner/владелец/команда либо Markdown-таблица связывает компонент с владельцем, отличающимся от другого источника. Сопоставление идёт по ID или названию; результат — candidate, требующий проверки.

**relation-disagreement**: явные утверждения о связи или её протоколе несовместимы. Поддерживаются структурированные links, Markdown-таблицы source/target и строки с точными ID и стрелками, в том числе отрицанием. Документные результаты всегда требуют проверки; простое отсутствие ссылки не считается отрицанием.

Отдельные dangling endpoints видны в графе и проверяются runtime-правилами SEAF; этот отчёт сосредоточен на несовместимых утверждениях из источников.

## Пример ShopFlow

В модели `demo.shop.delivery` имеет title **Delivery Service**, owner **Logistics**, источник `architecture/components.yaml`.

На временной учебной копии добавьте в зарегистрированный Markdown-документ искусственную строку:

```text
Delivery Service — владелец: Checkout Team
```

После применения такой документации проверка должна показать owner-disagreement с двумя источниками. Сначала убедитесь, что строка не является цитатой прошлого состояния или примером; только затем готовьте исправление. Пример внутри fenced code block этой инструкции игнорируется разбором Markdown-утверждений, чтобы сама справка не выдавала учебную строку за модельный факт.

В рабочем ShopFlow добавлять заведомо неверное утверждение ради демонстрации не требуется. Если находок нет, это корректный результат имеющихся проверок.

## Как использовать LLM

Внешний агент может сопоставить источники из grounded_context и дополнительных read_artifact/search_artifacts. Попросите привести обе несовместимые цитаты, версии и ID, отдельно пометить гипотезы. Правка после анализа требует обычного подтверждённого proposal.

## Ограничения

Сейчас это детерминированные проверки и разбор нескольких явных текстовых форматов; полноценное семантическое сравнение всех документов LLM не запущено. Одинаковые title у разных компонентов и исторические примеры могут давать неоднозначные кандидаты.

Источники включают доступные YAML-импорты и локальный Markdown. Находка содержит обе claims, источники, status/uncertainty; сохранение файлов не выполняется. Отсутствующие значения не считаются противоречием, а свежесть evidence проверяется перед возвратом находки. Не найдены противоречия не означает, что все артефакты согласованы. Runtime rules SEAF продолжают проверяться отдельно.
