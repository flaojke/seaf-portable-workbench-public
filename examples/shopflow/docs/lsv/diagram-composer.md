# Конструктор схем: сетевой, прикладной и компонентный уровни

Откройте **Конструктор схем** в рабочем пространстве. Он работает с активным проектом из раздела **Проекты**: локальной папкой или Git. Схема сохраняется в файлах проекта, а не только в браузере.

## Собрать схему

1. Нажмите **Новая схема**. Задайте уникальный ID, название и уровень: **Сетевой**, **Прикладной** или **Компонентный**.
2. В палитре выберите раздел модели, найдите объект по ID/названию и нажмите **Добавить объект**. Подпись и ссылка на исходную сущность сохранятся в определении схемы.
3. Если нужного элемента нет в архитектурной модели, можно добавить **визуальный узел**: например, условный шлюз или внешний участник. Новая сущность при этом автоматически не создаётся. В версии 2.3 инспектор также позволяет явно подготовить создание или изменение настоящего объекта и включить его в общий проверяемый черновик.
4. Перетаскивайте узлы на полотне. Доступен ввод X/Y, команда **Упорядочить**, масштаб, **Отменить/Повторить**. С клавиатуры выберите узел через Tab: стрелки перемещают его на 10 единиц, Shift+стрелки — на 50.
5. В блоке **Соединить узлы** выберите источник и получателя, укажите взаимодействие, протокол и данные. Связь можно изменить или удалить. Кнопка **Связи из модели** добавляет существующие `components.links` между выбранными компонентами; она не угадывает связи произвольной метамодели.
6. При необходимости добавьте зоны, например `external` и `internal`, затем назначьте их узлам. Зоны помогают читать схему; реальные политики безопасности и свойства объектов этим действием не меняются.

## Проверить и сохранить в файлы

Нажмите **Предпросмотр и файлы изменений**. Система проверит ID, ссылки на объекты, связи, количество элементов и коллизии файлов. Предпросмотр не меняет проект.

Далее: **Сохранить черновик для diff и проверки** → **Черновики** → изучить diff → проверить в SEAF → сохранить и обновить SEAF. Для Git-проекта создаётся локальный коммит; для обычной папки — локальная ревизия. Отправка в удалённый Git автоматически не выполняется.

Например, ID `shopflow-delivery` создаёт:

```text
root.yaml                                  # добавляется import, если его ещё нет
diagrams/composer/shopflow-delivery.yaml    # полное определение схемы и документ
diagrams/composer/shopflow-delivery.md      # Mermaid и таблицы объектов/связей
```

В YAML сохраняются уровень, узлы, ссылки на сущности, зоны, связи и координаты. В документе — Mermaid и читаемые таблицы. После применения документ появляется в **Архитектура → Схемы → выбранный уровень → название схемы (ID)**. ID в меню различает схемы с одинаковыми названиями.

Чтобы продолжить работу, выберите схему в списке **Сохранённая схема** и нажмите **Открыть**. Определение читается из YAML проекта. Измените элементы, повторите предпросмотр и обычный цикл проверки. Уже существующие посторонние файлы, документы и определения не перезаписываются: при коллизии потребуется другой ID.

## Пример ShopFlow: прикладной уровень

1. Выберите проект **ShopFlow**, ID схемы `shopflow-delivery`, название «Заказы и доставка», прикладной уровень.
2. Из раздела `components` добавьте `demo.shop.orders` (**Order Service**) и `demo.shop.delivery` (**Delivery Service**, владелец **Logistics**).
3. Нажмите **Связи из модели**: у Delivery появится существующая исходящая связь с Orders «Данные подтверждённого заказа / REST», протокол `HTTPS`. Это направление из исходного `architecture/components.yaml`, а не выдуманный вызов в обратную сторону. Для обсуждения будущей архитектуры можно добавить отдельную визуальную связь, явно отличая её от уже объявленной интеграции.
4. Расположите Delivery справа от заказов, проверьте предпросмотр и файлы, затем сохраните через проверенный черновик.

Ссылка на исходные сущности остаётся в YAML: `components / demo.shop.orders` и `components / demo.shop.delivery`. Отредактированная подпись на схеме не переименовывает исходный сервис.

## Пример: сетевой уровень

Создайте `shopflow-network`, сетевой уровень. Добавьте визуальные узлы «Интернет-клиент», «Пограничный шлюз» и «Внутренний контур», соедините их с явными подписями `HTTPS` и `TCP`, назначьте зоны `external`/`internal`. Если проект содержит настоящие сетевые сущности, выбирайте их из соответствующего раздела палитры вместо визуальных узлов.

Это пример представления: конструктор не утверждает, что такие устройства уже существуют в ShopFlow, не назначает IP-адреса и не создаёт реальные сетевые политики. Подтверждённые технические факты следует хранить в исходной метамодели проекта.

## Пример: компонентный уровень

Создайте `shopflow-order-components`, компонентный уровень. Добавьте существующие компоненты проекта. Если внутренние модули Order Service ещё не описаны, создайте их редактором и добавьте из палитры; для предварительного обсуждения допустимы явно визуальные «API», «Обработчик заказов», «Хранилище». Укажите связи и данные, затем сохраните через diff и проверку.

## Ограничения

- До 200 узлов, 500 связей и 30 зон в одной схеме; координаты — 0–20000. Большую архитектуру удобнее разделить на контексты.
- ID не должен быть зарезервированным именем Windows (`CON`, `NUL`, `PRN`, `AUX`, `COM1`–`COM9`, `LPT1`–`LPT9`). Коллизии файлов и ID отклоняются. Дополнительные неизвестные свойства формата также отклоняются, чтобы не удалить вручную внесённые данные незаметно.
- Выбор уровня задаёт смысл представления, но не конвертирует метамодель и не угадывает физическое размещение. Для КАДЗО, SEAF TA или собственной модели выбираются её реальные разделы и объекты.
- Сохранённые координаты применяются в конструкторе; Mermaid в Markdown использует собственную автоматическую раскладку.
- Markdown рядом со схемой генерируется заново из YAML при каждом сохранении. Постоянные ручные пояснения храните в отдельном документе; их перенос или удаление в генерируемом файле будет виден в diff.
- Изменение оформления само по себе не удаляет объекты и не переписывает `components.links`. Явные операции модели из инспектора версии 2.3 входят в общий diff. Подробности: [Интерактивный редактор схем](/entities/docs/blank?dh-doc-id=local.lsv.diagram-editor).
- Если проект изменился после предпросмотра, сохранение старого предпросмотра блокируется. Повторите его, изучите новый diff и проверьте модель.
- Эскиз автоматически сохраняется в текущем браузере; это не Git-коммит и не резервная копия. При ошибке локального хранилища не закрывайте страницу до сохранения серверного черновика.
- Read-only проекты можно просматривать и использовать для локального эскиза; запись отключена. SVG скачивается локально, без публикации или передачи внешним сервисам.
