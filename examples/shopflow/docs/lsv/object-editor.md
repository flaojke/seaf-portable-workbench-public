# Редактор систем, потоков и интеграций

Раздел **Редактор** находится в левом меню SEAF. Рабочий проект выбирается в **Проектах** или в верхнем списке рабочего пространства.

## Создать или изменить объект

1. Выберите раздел модели. **Создать систему** подготавливает компонент с типом `system`; **Создать** — объект выбранного раздела.
2. Укажите уникальный ID. Заполните название, владельца, описание и другие поля формы.
3. Если схема содержит enum, ссылку на объекты или объявленный справочник, поле отображается выпадающим списком. Значения, найденные у существующих объектов, предлагаются как подсказки. **Обновить справочники** перечитывает определения.
4. Дополнительные и вложенные свойства доступны в JSON. **Изменить указанные свойства** сохраняет остальные поля; **Заменить все свойства** заменяет объект целиком; **Удалить объект** показывает последствия удаления.
5. Нажмите **Показать изменения**, изучите семантический и файловый diff, затем **Проверить в SEAF**. Только успешная проверка разрешает **Сохранить и обновить SEAF**.

В локальном проекте сохраняется ревизия без Git; в Git-проекте — локальный коммит. Для пакетной операции отметьте объекты в таблице: связанные изменения проходят одну проверку и одно применение.

## Информационные потоки

В нижней части редактора показаны потоки из `components.*.links`. Выберите источник и получателя из списка компонентов, название и протокол. **Создать поток** или **Изменить** готовит diff настоящих links, используемых существующими схемами. Неизменяемые атрибуты связи сохраняются. Перенос источника формирует связанное изменение обоих компонентов; **Удалить** удаляет только выбранную связь.

Если проект использует отдельный тип интеграции, например `seaf.app.integrations`, выберите соответствующий раздел модели. Редактор использует доступную схему такого типа; неподдерживаемые конструкции JSON Schema остаются в JSON, а не превращаются в выдуманный справочник.

## Пример ShopFlow

Выберите `demo.shop.delivery`, измените команду-владельца на нужное значение и проверьте diff. Затем в таблице потоков найдите связь заказов с Delivery Service, нажмите **Изменить**, уточните название взаимодействия и протокол. После проверки и сохранения откройте сценарий оформления заказа и контекст компонентов. Описание последовательности в Markdown/Mermaid — отдельный артефакт: изменение links не переписывает его автоматически.

## Ограничения

Форма покрывает распространённые скалярные поля, enum и ссылки; сложные вложенные структуры редактируются в JSON. Поля неизвестного типа не удаляются. Проверка сопоставляет итоговую модель и валидаторы проекта; локальное сохранение черновика не означает, что модель проверена или опубликована. Read-only проекты доступны для просмотра. Неподтверждённое обновление портала можно повторить без второго коммита или ревизии.

## Если редактор показывает «Неизвестный тип документа»

Сообщение `Неизвестный тип документа [lsv-workbench]` означает, что открытый портал не загрузил модуль рабочего пространства. Например, прежний ярлык может запускать исходный Docker-образ SEAF вместо переносимой сборки форка. Успешный ответ `/health` сам по себе не проверяет наличие редактора.

1. Запустите `Start.cmd` из актуального переносимого комплекта и используйте адрес, открытый этим запуском. Node.js и необходимые модули уже включены.
2. Откройте **Редактор → Объекты и потоки**. Должны появиться выбор проекта, список объектов, свойства и кнопки изменения. При открытии старой вкладки обновите её через Ctrl+F5.
3. В **Проектах** проверьте выбранный проект, его папку и доступность записи. Существующую папку подключают без переноса файлов; Git-история остаётся в ней.
4. Если интерфейс не появился, проверьте `data/launcher-error.json`, состояние Workbench и адрес текущего портала в `data/run.json`. Не публикуйте run.json: он содержит локальный управляющий токен. Останавливайте только свой комплект через `Stop.cmd`.

**Пример:** выберите ShopFlow, найдите `demo.shop.delivery` (Delivery Service), проверьте владельца `Logistics`. Измените описание, нажмите «Показать изменения», изучите diff, затем «Проверить в SEAF» и «Сохранить и обновить SEAF». Изменение Git-проекта создаёт локальный коммит; push выполняется отдельно.

**Ограничения:** плагин редактора должен входить в сборку портала, а Workbench должен быть доступен по адресу, указанному этой сборкой. Смена runtime не превращает ранее проверенное предложение в проверенное для новой версии — создайте и проверьте его заново. Исторический снимок проверяет свои исходные байты; его preview может потребовать прежний runtime с точным совпадением identity. В переносимой поставке используются свободные локальные порты, поэтому адрес другого экземпляра может отличаться.
