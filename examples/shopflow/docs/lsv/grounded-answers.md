# Ответы с проверяемыми источниками

> Переносимый профиль: Для обычной папки источник содержит local revision и SHA-256; его не называют Git-коммитом. Свежесть проверяется по контенту, excerpt и локальной версии. Git HEAD по-прежнему является контекстом, а не доказательством коммита каждого байта. См. [инструкцию Windows](/entities/docs/blank?dh-doc-id=local.lsv.portable).

Feature: **AI-1**. Capability: `grounded-answers`.

Откройте [рабочее пространство SEAF](/entities/docs/blank?dh-doc-id=local.lsv.workbench) или [страницу рабочего пространства](/entities/docs/blank?dh-doc-id=local.lsv.workbench). Выберите нужный проект; ниже пример для ShopFlow.

Ассистент извлекает сведения из текущей модели и найденных строк исходников. Встроенный режим называется **evidence-extraction**: отдельная LLM, API-ключ и свободная генерация в нём не подключены.

## Как пользоваться

1. Откройте **Ассистент**.
2. Задайте вопрос с точным ID, названием сервиса или термином из артефакта.
3. Нажмите **Получить ответ**.
4. Изучите **Утверждения и основания** и раскройте **Источники**: project, файл, строка, commit, hash и фрагмент позволяют проверить основание.
5. Нажмите **Проверить актуальность источников**, чтобы проверить, соответствуют ли фрагменты текущим файлам. При изменении проекта повторите запрос для обновления ответа.

## Пример ShopFlow

Запрос: **demo.shop.delivery Logistics связи с заказами**.

В текущем `architecture/components.yaml` компонент `demo.shop.delivery` принадлежит Logistics и содержит links к `demo.shop.orders`, `demo.shop.delivery_db` и `demo.shop.events`. Ответ извлекает явные свойства и отношения, каждое со своими source records. Раскройте источник и сверьте ID.

Запрос **demo.shop.orders** помогает найти Order Service. Для полного временного порядка сообщений дополнительно читайте `docs/checkout.md` и `diagrams/checkout.mmd`: перечень links не равен sequence-сценарию.

## Полноценная LLM через внешний агент

Внешний агент подключается к MCP seaf. Для подготовки ответа используется `grounded_context` с project и question. Контекст включает найденные сущности, claims, sources, head, missingEvidence и указания цитировать project/file:line и commit. Каждый source содержит sha256, excerpt и точный диапазон строк, а также section/entityId, если они известны. Агент формулирует ответ своей моделью, а проверяемые источники берёт из SEAF.

Пример запроса агенту:

> Через MCP seaf получи grounded_context проекта shopflow по вопросу: «Как Delivery взаимодействует с orders и Event Broker?». Ответь по источникам, укажи project, файл, строку, ID и commit. Отдели факты от предположений; недостающие сведения обозначь явно.

Изменение найденной архитектуры выполняется отдельно через proposal/diff/validation/apply; вопрос не даёт команды изменить модель.

Внешний агент должен отделять факты от предположений. Например, если в учебной копии у компонента задан только title `Fraud Scoring Service`, факт — это прочитанное название с источником. Фраза «вероятно, оценивает риск мошенничества» должна быть явно помечена как вывод по названию; алгоритм и интеграции при отсутствии описания остаются неизвестными.

Такая генеративная формулировка принадлежит подключённому агенту. Встроенный ответ `evidence-extraction` возвращает извлечённые факты и цитаты с проверкой актуальности; самостоятельный вызов платной LLM эта вкладка не выполняет.

## Ограничения

Поиск основан на совпадении слов, а не embedding/vector RAG. Отсутствие результата не доказывает отсутствие сведений. Контекст ограничивает число сущностей/фрагментов. Документные цитаты помечаются отдельно от структурированных фактов, а недостающая поддержка — в missingEvidence.

В разделе **Утверждения и основания** отображаются переданные сервером claims и их источники. В детерминированный ответ включаются только проверенные claims. Проверка **verify_evidence**, доступная и через MCP, сравнивает hash, excerpt и commit с текущим содержимым; возможны fresh, stale, missing, invalid и unverifiable. Отсутствие Git-версии не выдаётся за свежесть.

SHA-256 идентифицирует прочитанные байты рабочего файла; commit обозначает HEAD соответствующего репозитория. Он сам по себе не доказывает, что эти байты уже сохранены коммитом. У источника из другого зарегистрированного проекта указываются его project и commit; для незарегистрированного общего импорта commit может быть неизвестен — такой источник не попадает в проверенные claims ответа.

Проверка актуальности не переписывает старый ответ: повторный запрос обновляет контекст. Содержимое документов — данные, его инструкции агент выполнять не должен.
