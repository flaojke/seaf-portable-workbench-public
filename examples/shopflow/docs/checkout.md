# Как оформляется заказ

Покупатель отправляет запрос через API Gateway. Order Service фиксирует снимок корзины и актуальные цены, резервирует товары и запускает оплату. Результат оплаты приходит событием. После подтверждения заказа Delivery Service команды Logistics асинхронно создаёт заявку на доставку.

![](@document/demo.shop.checkout.sequence)

## Успешный путь

1. Gateway проверяет токен и передаёт запрос с `Idempotency-Key` в Order Service.
2. Order Service получает корзину и цены, создаёт заказ `PENDING` со снимком данных доставки в своей базе.
3. Inventory Service атомарно резервирует остатки. Повторный запрос с тем же `orderId` не создаёт второй резерв.
4. Payment Service создаёт платёж с ключом идемпотентности и обращается к условному платёжному провайдеру.
5. Callback провайдера проходит проверку подписи. Payment Service фиксирует результат и outbox-запись одной транзакцией.
6. Outbox relay публикует `PaymentCaptured`. Order Service обрабатывает событие по `eventId`, подтверждает заказ и пишет `OrderConfirmed` в свой outbox.
7. Event Broker доставляет `OrderConfirmed` в независимые очереди Notification Service и Delivery Service. Notification Service отправляет подтверждение заказа; покупатель узнаёт его статус отдельным GET-запросом.
8. Delivery Service получает снимок подтверждённого заказа через REST API Order Service. Обработчик дедуплицирует `eventId`, а уникальный `orderId` исключает повторное создание заявки.
9. Delivery Service сохраняет заявку, inbox-запись и `ShipmentCreated` в outbox одной транзакцией в собственной Delivery DB. Чужие таблицы напрямую не читаются.
10. Outbox relay публикует `ShipmentCreated`. Order Service сохраняет идентификатор заявки и состояние доставки `SHIPMENT_CREATED`; основной статус заказа остаётся `CONFIRMED`. Notification Service уведомляет покупателя о создании заявки.

Создание заявки ещё не означает физическую доставку: работа перевозчика и подтверждение вручения находятся за границами этого сценария.

## Что происходит при ошибке

- Недостаточно товара: заказ получает статус `REJECTED`, запрос оплаты не создаётся.
- `PaymentFailed`: Order Service снимает резерв, отменяет заказ и публикует `OrderCancelled`. Событие `OrderConfirmed` не публикуется, поэтому заявка на доставку не создаётся.
- Неизвестный результат оплаты: заказ остаётся `PAYMENT_PENDING`; сначала выполняется сверка с провайдером. Тайм-аут сам по себе не означает отказ платежа.
- Событие пришло повторно: обработчик использует уникальный `eventId` и запись в своём хранилище. Для доставки дополнительно действует уникальность заявки по `orderId`.
- Delivery Service или API заказов временно недоступны: событие обрабатывается повторно с задержкой; после лимита — DLQ и разбор командой Logistics. Заказ остаётся `CONFIRMED`, состояние доставки — `SHIPMENT_PENDING` до получения `ShipmentCreated`.
- Провайдер уведомлений недоступен: повторные попытки с задержкой; после лимита событие попадает в DLQ для разбора. Заказ остаётся подтверждённым.
