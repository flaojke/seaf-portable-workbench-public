# Точечные и пакетные изменения

> Переносимый профиль: Самостоятельный раздел «Редактор» добавляет формы, справочники и потоки. Сохранение поддерживает Git-коммит или локальную ревизию; выбранный provider определяется в «Проектах». Дополнительные свойства остаются доступны в JSON. См. [инструкцию Windows](/entities/docs/blank?dh-doc-id=local.lsv.portable).

Feature: **29**. Capability: `object-editing`.

Откройте [рабочее пространство SEAF](/entities/docs/blank?dh-doc-id=local.lsv.workbench) или [страницу рабочего пространства](/entities/docs/blank?dh-doc-id=local.lsv.workbench). Выберите нужный проект; ниже пример для ShopFlow.

Редактор работает с объектами разных разделов модели: `components`, `contexts`, `docs`, `aspects` и другими загруженными словарями. Для объекта доступны создание, изменение указанных свойств, полная замена и удаление.

## Точечное изменение

1. Откройте **Объекты**, выберите **Раздел модели**.
2. Найдите ID по строке поиска и нажмите на объект.
3. Выберите операцию. **Изменить указанные свойства** объединяет JSON с объектом, сохраняя остальные поля. **Заменить все свойства** использует JSON как полный новый объект.
4. Введите JSON. Помощник **Добавить** принимает имя свойства и JSON-значение, например owner и `"Logistics"`.
5. Нажмите **Показать изменения**, просмотрите свойства **Было / Станет** и файлы.
6. Нажмите **Проверить в SEAF**, затем — **Сохранить в Git и обновить SEAF**.

Для создания нажмите **Создать**, задайте новый ID и полный JSON. Для удаления выберите **Удалить объект**. Чтобы удалить отдельное свойство, откройте полный JSON существующего объекта, уберите поле и используйте **Заменить все свойства**.

## Пример ShopFlow

Выберите `components/demo.shop.delivery`. В режиме **Изменить указанные свойства** можно подготовить:

```json
{
  "owner": "Logistics",
  "description": "Доставка подтверждённых заказов, работа с ShipmentCreated и повторными попытками."
}
```

Существующие links и technologies сохранятся. Если owner уже Logistics, diff не должен показывать фиктивную смену владельца.

Для нового учебного компонента задайте `demo.shop.tracking`:

```json
{
  "title": "Tracking Service",
  "entity": "component",
  "kind": "microservice",
  "owner": "Logistics",
  "description": "Учебный сервис отслеживания статусов доставки."
}
```

Новое определение размещается в `architecture/workbench.yaml`, его импорт добавляется в root manifest автоматически. Включение нового сервиса в явные contexts или sequence-сценарий — отдельные правки; сам редактор их не придумывает.

## Пакетная операция

Отметьте несколько объектов флажками, выберите **Изменить указанные свойства** и задайте общий JSON. Например, выберите `demo.shop.delivery` и `demo.shop.delivery_db`, затем `{"owner":"Logistics"}`. Все выбранные ID попадут в один серверный черновик, diff и проверку. Уберите флажки, чтобы вернуться к точечной работе.

## Ограничения

Массив при обычном merge заменяется целиком: изменение links требует передать весь нужный список. Полная замена удаляет отсутствующие поля; сначала прочитайте объект. При удалении интерфейс показывает найденные ссылки на объект и их исходные файлы в блоке **Ссылки на удаляемые объекты — проверьте последствия**. Валидация блокирует несогласованный результат. Автоматического cascade delete нет; найденный список не заменяет проверку всех документов и правил проекта.

В редакторе можно выбрать существующий раздел или указать новый в поле **Новый раздел модели**. Имя должно начинаться с латинской буквы и содержать буквы, цифры, точку, дефис или подчёркивание. Поддержка нового типа в самом портале зависит от метамодели: серверная проверка остаётся обязательной.

Через MCP инструмент **propose_objects** принимает точечные/пакетные операции, включая removeProperties для явного удаления свойств. Сервер принимает до 500 операций, а стандартный MCP proposal — до 50 файлов. Read-only проекты не разрешают применение. Кнопка сохранения активируется только после успешной проверки; push не выполняется.

## Если коммит сохранён, а портал не обновился

В результате операции отдельно показаны сохранённый Git commit и статус reload. Если обновление портала завершилось ошибкой, восстановите доступность SEAF и нажмите **Повторить обновление SEAF** в панели черновика. Кнопка повторяет загрузку для уже сохранённого коммита, обновляет журнал предложения и сохраняет прежнюю идентичность Git-коммита.

Пример: при недоступном портале правка owner у `demo.shop.delivery` может получить статус `committed_reload_failed`. После восстановления портала retry должен вернуть `reload.status: updated` и пустой список проблем. Проверить историю и исходники можно в Git; отправка в удалённый репозиторий выполняется отдельно.
