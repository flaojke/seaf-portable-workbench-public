# Семантический diff архитектуры

> Переносимый профиль: Сравнение работает также между локальными ревизиями обычной папки. Нажмите «Обновить историю версий» и используйте ID ревизии; HEAD обозначает текущее состояние. Ссылки на исходные файлы и raw diff сохраняются. См. [инструкцию Windows](/entities/docs/blank?dh-doc-id=local.lsv.portable).

Feature: **1**. Capability: `semantic-diff`.

Откройте [рабочее пространство SEAF](/entities/docs/blank?dh-doc-id=local.lsv.workbench) или [страницу рабочего пространства](/entities/docs/blank?dh-doc-id=local.lsv.workbench). Выберите нужный проект; ниже пример для ShopFlow.

Сравнение группирует изменения по разделу, ID и пути свойства. Оно показывает добавленные/удалённые объекты и старые/новые значения, уменьшая шум от форматирования YAML.

## Как пользоваться

1. Откройте **Сравнение**.
2. Укажите **Базовую версию Git** и **Целевую версию Git**, например HEAD~1 и HEAD.
3. Нажмите **Сравнить версии**.
4. В таблице прочитайте объект, его исходные файлы, вид изменения, свойство, **Было** и **Станет**. Связь с файлами передаётся в `sourcePaths` каждого изменения.
5. Для подготовленного редактором черновика diff виден в **Предварительном просмотре**. В **Сравнение** также доступна кнопка **Сравнить черновик**, если он выбран.
6. Перед commit изучите **Текстовый diff файлов** и **Изменяемые файлы** в панели черновика.

## Пример ShopFlow

В **Объекты** выберите `components/demo.shop.delivery`, **Изменить указанные свойства**, подготовьте новое description и нажмите **Показать изменения**.

Ожидается строка для `demo.shop.delivery`, kind **Изменён**, property **description**, старый и новый текст. technologies и links не должны измениться, если вы их не передавали. До проверки и применения это только предложенное состояние.

Для сравнения уже сохранённых версий используйте commit до добавления Delivery и commit после него: в результате появится добавление компонента и связанных сущностей/свойств.

Результат сравнения также содержит список изменённых файлов и обычный Git diff. Откройте **Текстовый diff исходных файлов**, чтобы проверить YAML, Markdown и другие текстовые артефакты, на которых основано сравнение.

## Правила сравнения

Порядок ключей YAML/JSON, отступы и комментарии не считаются изменением модели. Объектные словари сравниваются по ключам. Порядок обычных массивов, в том числе шагов сценария, значим. Список links с ID нормализуется для сравнения связей.

Смена ID без отдельной карты переименования показывается как удаление старого и создание нового объекта. Значения сравниваются по загруженным project imports.

## Ограничения

Это сравнение модели, а не смысловое понимание произвольного Markdown или Mermaid. Изменения текста документов внутри файлов смотрите в файловом diff; ссылка docs.source сама по себе не отражает изменившееся содержимое Markdown.

Сравнение Git ref использует текущие общие слои validation workspace вокруг выбранной версии project Git. Оно не восстанавливает исторические версии всех внешних репозиториев. Для фиксации полного локального набора источников нужен снимок.
